The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.0.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Under evaluation - whether AVML should be the default first choice

The dual mechanism in 2.0.0 tries LiME first. The paired trial below was run to
decide whether to reverse that, and it does not support reversing it on
reliability grounds - so the default stays as it is.

Putting AVML first remains attractive for a different reason: it would avoid
loading a kernel module into a possibly compromised host at all, it was
consistently faster, and it ships an `aarch64` build the LiME path does not have.
That is a change of default posture rather than a bug fix, so it wants its own
decision and its own release. Reordering needs no code change - set
`memoryAcquisitionTools` to `avml,lime` in `cdk.json`.

## [2.0.0] - 2026-08-21

Major version. The analysis host's operating system and toolset change, the
Lambda runtime changes, and three inputs change shape in ways an existing
deployment or deploy script will notice. Read the breaking changes before
upgrading.

### Breaking changes

- **`forensicImageName` is renamed from `sansift` to `forensic-analysis-ami`, and that value *is* the physical name of the SSM parameter `createForensicInstance` reads.** The upgrade creates the new parameter and deletes the old one, so **any AMI id written into `sansift` outside CloudFormation is discarded** and no investigation can launch an analysis instance until the image pipeline publishes an AMI or `ec2ForensicImage` is set. To keep the existing parameter and its value, set `forensicImageName` back to `sansift` in `cdk.json` before deploying
- **The forensic analysis host is Amazon Linux 2023 with a targeted toolset, not Ubuntu with SANS SIFT.** Everything the orchestrated workflows invoke is present and asserted at image build time, but Autopsy, The Sleuth Kit, `bulk_extractor`, `foremost` and `binwalk` are not, and `hfsplus` cannot be mounted. See the analysis host section of the README before relying on hand analysis on a retained host
- **The cross-account prerequisite template's `solutionInstalledAccount` and `solutionAccountRegion` parameters are now required and pattern checked.** They previously defaulted to `123456789012` and `us-west-2`. Any pipeline that deployed `cross-account-role.yml` without passing both will now fail up front, naming the parameter - which is the point: the region default was interpolated into the role's trust policy, so leaving it produced a policy naming `triage-us-west-2-Role` and a rollback that named neither the parameter nor the region. `kmsKey` is now optional and its statement is omitted when empty
- **`forensicInstanceType` is a comma-separated preference order, not a single instance type.** A single value still works and is then the only type tried
- **The Lambda runtime is Python 3.12**, from 3.9, which reached end of support on 2025-12-15
- **`Forensic-Profile-Function` accepts `RHEL8`, `AL2023` and `AL2`.** It previously accepted `RHEL7`, `RHEL8` and `RHEL9`; `RHEL7` and `RHEL9` had no document and no environment variable, so they passed validation and then raised `KeyError` after launching a builder instance the handler does not terminate. `AL2` now works for the first time
- **The evidence volume is mounted read only.** Any local customisation that wrote to the mount point will fail
- Red Hat support is **RHEL 8 only**. 7 and 9 were never wired; see the README support matrix for the exact failure modes

### Added

- **Linux memory is acquired by two independent mechanisms, LiME and AVML, and a capture that cannot be read is rejected rather than reported as success.** LiME intermittently returned a full-size image whose pages were almost entirely zero and which contained no kernel banner - 3 of 9 acquisitions observed here, across Amazon Linux 2 kernel 4.14 and Amazon Linux 2023 kernels 6.1 and 6.18, cause not isolated. Retrying LiME would share whatever that cause is; AVML does not, because it reads `/dev/crash`, `/dev/mem` or `/proc/kcore` rather than loading a kernel module. `memoryAcquisitionTools` (context key in `cdk.json`, `lime,avml` by default) sets which tools are tried and in what order, and the **kernel banner check decides whether to move on**, not the exit status - the failure being guarded against exits 0, so a fallback keyed on exit status would never fire. Details that matter for evidence:
  - **nothing is written to the disk of the machine under investigation, by either tool.** This was the open question when AVML was first evaluated: `avml stream` has no S3 target, and where LiME listens and is connected to, AVML connects outward. Rather than write a RAM-sized file to a possibly compromised host, or use `--url` with a presigned PUT (capped at 5 GB for a single PUT, so it fails on any sizeable instance), the document runs a short `python3` listener - present by default on every distribution supported here, so it installs nothing - and streams from it to S3 exactly as the LiME path does
  - **both tools are pinned and AVML is verified by digest before it is made executable.** LiME is cloned at tag `v1.12.0` from `jtsylve/LiME`; note `504ensicsLabs/LiME` now redirects there, and cloning the old path works only while GitHub honours that redirect. AVML is release `v0.20.0`, SHA256 checked against a pin obtained from two independent downloads. An operator-staged binary under `tools/avml/` is used as-is, which is the operator's provenance and is what lets a host with no route to GitHub still be imaged - the same contract the RHEL path already uses
  - **which tool produced the evidence is recorded on the object**, as `acquisition-tool`, `acquisition-tool-version`, `acquisition-tool-origin` and `acquisition-attempt` S3 metadata. Both tools write LiME format - verified from the header magic `454d 694c` - so Volatility 3 reads either through the same layer and no downstream component needs to know which ran; an examiner does
  - **a rejected capture is never deleted.** It remains as a previous version of the object, which the artefact bucket has always kept
  - **the fallback does not depend on assumptions about the target host.** Three that would each have removed it silently: the listener resolves an interpreter (`python3`, then `python2`, then `python`) rather than hardcoding `python3` - the stock Amazon Linux 2 AMI has both, but the `amazonlinux:2` container image has only python2.7, and AL2 kernel 4.14 is one of the kernels LiME failed on, so it is the last place to trade a working fallback for an assumption; the AVML binary is relocated to `/var/tmp` or `/run` when its working directory is mounted `noexec`, because CIS hardening puts `noexec` on `/tmp` and `chmod` cannot undo a mount option; and the loop **refuses to start an attempt it cannot finish** inside the step's `timeoutSeconds`, estimating from the previous attempt's own duration, because one capture used to have the whole budget and two attempts now share it - an attempt killed mid-stream yields neither a capture nor a diagnostic, so it says how much budget is left and names `ssmExecutionTimeout`
  - **the investigation reports which tool acquired the image**, alongside the kernel it already reported. Echoed and explicitly labelled as reported by the acquiring host rather than independently verified: those values were written on the machine under investigation, with credentials that machine held, so they corroborate provenance and are never used in a decision
  - Verified across 16 cases in a container - each tool succeeding first, each falling back to the other on a banner-less capture, on a capture below the size floor and on a module that will not load, both failing, an unknown tool name, a single-tool list, an empty list, an unreachable download, a digest mismatch, a python2-only host, a `noexec` working directory, an exhausted step budget and a non-numeric one - with the published digest confirmed to be the digest of the *accepted* capture in both the first-attempt and post-fallback cases

- **A paired reliability trial of the two mechanisms, 36 live acquisitions.** Six runs per tool on each of three hosts - Amazon Linux 2023 kernel 6.1.180, Amazon Linux 2023 kernel 6.18.41, and Amazon Linux 2 kernel 4.14.355 - interleaved on the same instances so host drift hit both tools equally. Results, and the reason the default did not change:
  - **LiME 18/18 usable, AVML 18/18 usable.** The intermittent LiME failure that motivated the fallback - 3 unusable captures in 9 acquisitions, observed earlier on these same kernel lines - **did not reproduce once**. It remains real and remains unexplained; this trial did not measure it, so nothing here shows AVML to be the more reliable mechanism, and the fallback is insurance against a failure that has been seen rather than a fix for a measured rate
  - **Both mechanisms produce captures Volatility 3 analyses identically.** On the AL2 host, `banners.Banners` found the kernel at the *same three offsets* in both images (`0x1c00180`, `0x37ad434`, `0x771e5618`), and `linux.pslist` walked 104 processes in the LiME capture and 101 in the AVML one, 85 of them common - the differences are all in the transient high-PID range, consistent with two captures of a live host taken a minute apart rather than with any loss of coverage
  - **The images are not byte-identical, and should not be expected to be.** On a host reporting 1.893 GiB, LiME wrote 2,107,145,280 bytes and AVML 1,855,487,487: the two enumerate physical ranges differently, LiME including ranges beyond usable RAM. Because the LiME format carries range headers, the addressing still lines up, which is what the identical banner offsets demonstrate
  - **AVML was consistently faster**: median 66 s against LiME's 80 s for a ~1.9 GiB host, min 64 s in both cases, max 82 s against 98 s
  - **Extended to instances whose physical memory spans the 4 GiB boundary**, since every host in the 36-run trial was a t3.small with one contiguous System RAM range below it - and a partial-capture bug that only appears with several ranges is the shape of "full-size image, almost all zeros". An 8 GiB and a 32 GiB host, both with four System RAM ranges including one above 4 GiB, were captured by both tools: four for four usable, so that hypothesis is not supported either. A 30.8 GiB host took LiME 197 s and AVML 88 s, so two attempts fit inside the default 1800 s budget with room - on a freshly booted host, whose free pages compress away; a host with mostly non-zero memory takes proportionally longer through a single-threaded `gzip`, which is what the budget guard is for
  - **AVML writes a much smaller file than LiME and loses no evidence doing so.** On the 8 GiB host LiME wrote 8,418,013,312 bytes and AVML 1,690,352,828 - five times smaller - because neither `/dev/crash` nor `/dev/mem` exists on Amazon Linux 2023, so AVML reads `/proc/kcore` and writes only mapped ranges, while LiME writes every physical range including free pages. Compressed they are within 4% (619 MB against 598 MB), which is the tell: LiME's extra 6.7 GiB is almost entirely zeros. Volatility 3 confirmed it is not a coverage loss - the kernel banner appears at the *same* offsets in both, above the 4 GiB boundary, and the plugins that must read **user-space** pages recover comparable results: `linux.psaux` 124 against 121 processes, both with full argv strings read from the user stack, `linux.envars` 476 against 447, `linux.lsof` 1788 against 1741, `linux.proc.Maps` 4343 against 3750. The residual differences are the same order as the process-list drift between two captures of a live host taken a minute apart, so this comparison cannot separate the last few percent from that drift
  - Provenance was recorded correctly on all 36 objects and distinguished all three resolution paths - `staged` for the pre-built LiME modules, `built-from-v1.12.0` where the pinned clone was compiled in the guest (AL2 4.14), and `release-v0.20.0` for every AVML run, each of which downloaded the real binary from GitHub and verified it against the pinned digest. Digest integrity was confirmed by recomputing from the stored objects

- **Continuous integration.** Nothing ran the test suites automatically until now, which mattered because most of what they assert was learned from live AWS runs and cannot be rediscovered by reading the code. `.github/workflows/ci.yml` runs tsc, ESLint, flake8, mypy, the Python suite with the Makefile's own `--fail-under=80` coverage gate, the TypeScript suite, cfn-lint on the prerequisite template, and `cdk synth` - which needs no AWS credentials, because the app takes every value it needs from `cdk.json`. The workflow pins Python 3.12 deliberately: `make install` rebuilds `.venv` with whatever `python` resolves to, and `check-py-version` inspects the *old* venv before that rebuild, so on a machine where `python` is not 3.12 the suites run green against the wrong interpreter. Rehearsed end to end in a clean 3.12 virtualenv before being committed. `black`, `isort` and `prettier` are **not** gated yet - they fail on 6, several and 119 files this project has never formatted, and a CI that is red on its first run is a CI people learn to ignore; format the tree in its own change and add them then
- **`NOTICE.txt` attributes the forensic tooling fetched at runtime.** LiME (GPL-2.0), AVML (MIT), Volatility 3 (VSL), dwarf2json (MIT), plaso (Apache-2.0), pefile (MIT) and winpmem (Apache-2.0), each with the version this release pins, and an explicit statement that none is redistributed here - every one is downloaded or built into the deploying customer's own account at acquisition or investigation time. The GPL-2.0 LiME module is compiled and loaded on the instance under investigation and is not linked into or derived from this solution's code
- **Amazon Linux 2 symbol table generation, via `Forensic-Profile-Function` with `distribution: AL2`.** Previously impossible: the handler built the document's environment variable name by concatenating the distribution string, and Amazon Linux 2's document is `amazon-linux-2-volatility-profile.json`, so the CDK names its variable `AMAZON_LINUX_2_VOLATILITY_PROFILE` - a name `"AL2"` cannot produce. The document itself always worked; verified again on a live AL2 instance producing a 25 MB, 102,393-symbol table for kernel 4.14.355

- Amazon Linux 2023 support for memory forensics. `AL2023-volatility-symbol.json` builds a Volatility 3 symbol table on AL2023, resolving the per-kernel-line package names (`kernel6.18-devel`, `kernel6.18-debuginfo`) that AL2023 uses from the 6.12 line onwards with a fallback to the legacy unversioned names, and validating the generated ISF file before upload. `AL2023` is now accepted by the `Forensic-Profile-Function` state machine
- A synth-time guard that fails the build when the Lambda dependency layer exceeds Lambda's 250 MB unzipped limit, and warns above 90%

### Security review

2.0.0 was scanned against the AWS Content Security Review rubric. Everything it
found was either fixed - credential logging, unpinned upstream fetches, a Bandit
false positive, and the data-handling items - or accepted deliberately, justified
at the statement that grants it, and recorded with its residual risk in the
"Permissions this solution holds deliberately" table in the README.

Four grants are accepted because removing them removes a containment or
collection step rather than a permission:

- `iam:PutRolePolicy` on `role/*`, because isolation attaches a deny-all inline
  policy to the instance profile role of whichever instance turns out to be
  compromised, which is unknown at deploy time and for which IAM offers no
  condition key. **Restrict who may invoke the isolation Lambda or assume the
  cross-account role, and alert on `iam:PutRolePolicy` in CloudTrail.**
- All-port ingress from `0.0.0.0/0` on the isolation security group, because
  matching *all* traffic is what moves an instance's existing flows from tracked
  to untracked so that isolation drops an attacker's established session instead
  of leaving it open. Narrowing the CIDR defeats the mechanism.
- `ssm:SendCommand` on any instance, bounded by the document scoping above.
- `ec2:RunInstances` and `ec2:CreateTags` on `*`, because the analysis host's AMI,
  subnet and security group are resolved at investigation time.

The first two carry `cdk-nag` suppressions with these reasons attached, so the
decision is machine-readable and auditable rather than implicit.

### Known issues

- **`lambda/src/recorder/app.py` is unreferenced.** No CDK construct creates a Lambda from it and neither synthesized template contains a function with a recorder handler; the AMI id reaches SSM through the Image Builder distribution configuration instead. It is left in place rather than deleted, but note that it reads `IMAGE_SSM_NAME` and its test pins the pre-2.0.0 parameter name `sansift`, so it would write to the wrong parameter if it were ever wired up. It also swallows a `put_parameter` failure and returns 200, which for an SNS-triggered function would suppress the retry, and it indexes `outputResources.amis[0]` unguarded - a failed image build's notification carries no AMI.

### Changed

- Generated coverage reports are no longer tracked in git. A public clone carried build artefacts, and a stale coverage XML in the repository invites a reader to trust a number nothing produced

- Lambda runtime migrated from Python 3.9, which reached end of support on 2025-12-15, to Python 3.12
- The dependency layer is now built for the Lambda execution environment (`--platform manylinux2014_x86_64`, `--only-binary`, `--python-version`) instead of the build host. Synthesizing on macOS previously produced Mach-O objects in the layer
- Test and security tooling (`pytest*`, `bandit`) moved out of `lambda/requirements.in` so it no longer ships to production; `kubernetes` pinned below the release that adds an unused asyncio client. Layer is now 78.9% of the size limit, down from 107.9%
- Python and Node dependencies refreshed; `npm audit` findings reduced from 8 (5 high) to 0. `urllib3` moved off the 1.26 line, which carried four high-severity advisories and could not be upgraded while the runtime was Python 3.9 on Amazon Linux 2
- In-guest Python provisioning in the SSM documents no longer compiles Python 3.9.16 from source or repoints `/usr/bin/python3`, which breaks the host package manager. A supported interpreter is installed from the distribution instead. RHEL documents no longer pin the retired `python3.8` stream
- Subscription-manager credentials are now required only for Red Hat distributions
- The forensic tools builder runs on `t3.large`, matching the sibling kernel symbol builder for the same workload

### Fixed

- **Credentials were written to CloudWatch Logs by two handlers, and 21 logged their whole payload.** `runForensicsCommand` logged the `params` dict it sends to Systems Manager, containing the `AccessKeyId`, `SecretAccessKey` and `SessionToken` it had just obtained from `AssumeRole`; `kernelSymbolLoader` logged its raw event, which for a Red Hat target carries the customer's Red Hat subscription username and password - not a short-lived AWS credential but a long-lived one belonging to someone else. Both were found by a security review rather than by anything in the build. `common/redact.py` now masks secret-valued keys while keeping the payload shape that makes these logs worth having, every handler uses it, and a test walks the tree and fails if any handler logs a raw payload again. Verified in production logs after a live run: `ssm parameters {'AccessKeyId': '***REDACTED***', 'SecretAccessKey': '***REDACTED***', ...}` with the diagnostic fields intact, and no session-key material in any log group
- **One failing corroborating Volatility 3 plugin no longer voids a memory investigation.** The rule was "any plugin failed, fail the case", which is the mirror of the bug it was introduced to fix. Found by a live end-to-end run: on Amazon Linux 2023 kernel 6.18.41, `linux.bash` crashes inside Volatility 3 itself - `AttributeError: 'NoneType' object has no attribute 'i_size'` walking a VMA with a null inode, an upstream defect - and the investigation reported `MEMORY_INVESTIGATION_FAILED` having produced and uploaded a process list, argv, a scan-based process list and a plaso timeline. It would have done so for **every** memory investigation on the current default AL2023 AMI. `linux.pslist` is now essential and the rest corroborating: only an essential failure voids the case, the "no plugin produced output" floor stays, and the failed plugins are always named so the gap is known rather than inferred
- **Twelve unpinned upstream fetches across six documents.** The pins introduced for the acquisition path never propagated: `volatility3` now `v2.28.0`, `dwarf2json` `v0.9.0`, `pefile` `2024.8.26`, LiME `v1.12.0` from `jtsylve/LiME`, in `AL2023-lime-volatility-loader`, `AL2023-volatility-symbol`, `amazon-linux-2-lime-volatility-loader`, `RHEL8-lime-memory-load-investigation`, `RHEL8-volatility-symbol` and `windows-lime-memory-load-investigation`. The deprecated `pip3 install awscli` (v1, unpinned) is replaced by the official AWS CLI v2 archive. An unpinned clone builds whatever is at the tip of the default branch on the day of the incident, into the tooling that produces and reads evidence
- **`ssm:SendCommand` in the cross-account prerequisite is scoped to the forensic account's documents.** `SendCommand` authorises the document and the instance separately, so the policy is now split: documents are restricted to `arn:...:${solutionInstalledAccount}:document/*`, which stops the cross-account role invoking `AWS-RunShellScript` - remote code execution on any instance in the application account. The instance half stays unscoped because which instance is under investigation is not known until a finding arrives. **Redeploy `cross-account-role.yml` in each application account to pick this up**; a `cdk deploy` of the main stack does not
- **The analysis instance was tagged `Ubuntu`.** Its Name tag read `<type>_<id>_Ubuntu` and its volume `<id>_UbuntuVlm`, stale since the analysis host became Amazon Linux 2023. That tag is how an examiner identifies the host holding a case's evidence, so it now reads `_analysis`
- **AVML was downloaded as the x86_64 build regardless of the target's architecture.** The release ships one binary per architecture, so a Graviton target received an ELF it could not execute - and AVML was therefore unavailable on precisely the architecture where it is the only practical option, since LiME needs a kernel module and no `aarch64` module can be staged, only compiled in the guest. The document now selects `avml` or `avml-aarch64` from `uname -m`, pins a digest per asset, names an unsupported machine type instead of guessing, and records which asset ran in the capture's provenance. Verified on a live `m7g.large`: `acquisition-tool-origin=release-v0.20.0-avml-aarch64`
- **Pagination did not work on any list query in the GraphQL API, in two independent ways.** Both were confirmed against a deployed API: `timelineEventsForRecord` asked for `limit: 2` returned all six events, and `allForensicRecords` asked for `limit: 1` returned every record in the table.
  - Every resolver template read `$ctx.args.limit` and `$ctx.args.nextToken`, but the schema declares both **inside** the input object - `input.limit`, `input.nextToken`. The `#if` guards were therefore never true and both arguments were silently dropped.
  - The six `Query` templates also placed `limit` and `nextToken` **inside** the `"query"` object. The AppSync DynamoDB Query mapping-template reference puts them at the top level, as siblings of `query` alongside `index` and `scanIndexForward`, so AppSync would have ignored them there even had they been read. The `Scan` template placed them correctly, which is how the wrong pattern in the other six went unnoticed.

  For a forensic API this is not cosmetic. A case with more items than one DynamoDB page returned a truncated list *together with a `nextToken`* the caller had no way to use, so evidence past the first page was unreachable - and a caller that did implement paging was served the same first page indefinitely. After the fix, paging a six-event record two at a time returns three pages, six distinct events, no repeats, verified live. Trailing commas were also removed from the templates: `{"#PK": "PK", "#SK": "SK",}` and a `},}` in the GetItem key are not valid JSON, and AppSync happened to tolerate them.

  `test/api-resolver-templates.test.ts` now renders every template with and without each optional argument, asserts the result parses as JSON, and asserts the schema and the resolvers agree about where the arguments live. Nothing validated these assets before: they are text uploaded to AppSync, so a wrong one produces no error at deploy time and no error at query time - it just quietly does something else.
- **One lookup for "is this instance registered with Systems Manager", replacing seven.** `DescribeInstanceInformation` returns **10** managed nodes by default, **50** at most, and it paginates - so asking it unfiltered and reading one response answers "no" in any account holding more managed nodes than one page, about an instance that is perfectly healthy. Four of the seven copies had been fixed to filter and paginate; three had not, and `runMemoryAnalysis` even carried a comment describing the fix while two other handlers kept the broken form. `common/managed_nodes.py` now owns it, batches to the filter's 50-value limit, distinguishes "not registered" from "could not ask" (an API error used to become "no SSM agent"), and `tests/common/test_managed_node_and_subnet_lookup.py` asserts no handler calls the API itself. What each broken copy did:
  - **`runForensicsCommand` sent no disk investigation commands at all and returned HTTP 200.** `is_ssm_installed` stayed `False`, the loop that sends the commands was skipped, and the function returned success anyway - so the investigation reported completion having produced nothing, and the absence of evidence surfaced later, on another host, possibly after the target was gone
  - **`checkInstanceStatus` reported a ready analysis instance as not associated with Systems Manager**, so the state machine waited on an instance that was already waiting for it
  - **`triage` raised `not able to accuire instance detail info` for a registered instance.** Its call was filtered but not paginated, and an empty first page carrying a `NextToken` is a permitted response - which fails triage before any evidence is taken
- **An unreachable analysis host is now a failure rather than a quiet no-op.** In both investigation handlers the only success `return` sat inside `if is_ssm_installed:` with no `else`: `runMemoryAnalysis` fell out of the function and returned `None` - a null Payload for the state machine, which then fails the next state on a missing field instead of saying the host could not be reached - and `runForensicsCommand` returned 200 with no `ssmCommandList`. Both now raise, naming the instance
- **One lookup for the forensic subnet, replacing three, and it no longer raises `IndexError`.** All three handlers that launch an instance - the analysis host, the symbol builder and the deploy-time tools loader - filtered subnets on the `aws-cdk:subnet-name` tag and then indexed `["Subnets"][0]`. That tag exists because this solution's own VPC is built by the CDK; it does **not** exist when the solution is pointed at an existing VPC, which is a documented deployment mode (`isExistingVPC` resolves the VPC through `Vpc.fromLookup`, and the customer's subnets were not created by this app). The filter then matched nothing and all three failed with `list index out of range`, naming neither the tag, the VPC, nor the deployment mode. `common/vpc_lookup.py` raises `SubnetNotFound` naming all three and telling the operator which tag to apply. It also makes the choice deterministic: one subnet per availability zone matches, and taking whichever the API listed first let the launch AZ vary between runs of the same workflow
- **Reading a forensic record was truncated at one DynamoDB page, and the symptom was "does not exist".** A Query returns at most 1 MB of items and sets `LastEvaluatedKey`, and `_query` read a single response. That limit is reachable here because several timeline events store an entire AWS API response as their event data. What made it a hard failure rather than a lost tail is the sort order: a record's items share one PK and come back sorted by SK, and the keys are `ARTIFACT#`, `EVENT#` and `RECORD#` - so the `RECORD#` metadata item, the one the reader looks for to decide the record exists, sorts **last** and is the first thing to fall off the page. A case with a rich timeline therefore raised `DoesNotExistException` - "does not exist or has been deleted" - about a live forensic record
- **`resolve_artifact_metadata` classified digest files by their last filename fragment.** `for part in key.split("_"): is_sha_256 = "sha256" in part` has no `break` and no accumulation, so only the final fragment counted and `vol_sha256_part1.txt` was treated as *not* a digest file, sending the code looking for a digest of the digest. Its `list_objects_v2` call was also unpaginated
- **One resolver for "which SSM document does this instance need", replacing four.** Acquisition, acquisition completion, memory analysis and disk investigation each answered that question independently, and each copy carried its own version of the same three mistakes - which is exactly how the third and fourth copies survived the first two being fixed. `common/platform_dispatch.py` now owns all of it and `tests/common/test_platform_dispatch.py` asserts no handler re-derives any of it. What was wrong in each copy:
  - **`runMemoryAnalysis` had all three.** Its Red Hat branch used the same three ranges open at the lower bound, so RHEL 8.0 matched none of them and `rhel_version` was unbound; it built the environment variable by concatenating that version, so RHEL 7 or RHEL 9 raised `KeyError('RHEL9_LIME_MEMORY_LOAD_INVESTIGATION')`; and it looked the node's platform up in `instanceInfo` by id, assigning inside the loop with no else - so an EKS node absent from `instanceInfo` was analysed with the **previous node's** platform, and therefore possibly another distribution's document and symbol table
  - **`runForensicsCommand`** had the same unguarded lookup, leaving `platform_details` unbound and raising `UnboundLocalError` - after the investigation instance had already been launched. It also defaulted the disk document to the Linux one before deciding, so a Windows target whose platform lookup went wrong ran the *Linux* disk investigation rather than failing
  - **`checkMemoryAcquisition`** decided which document to *un*-share from a single `platform_details == "Windows"` comparison with no Red Hat case at all. Acquisition shares the selected document with the application account; completion removed the **Linux** document for a Red Hat target, so **the RHEL8 acquisition document stayed shared with the application account indefinitely** - a standing grant to the account that may be the compromised one. It also read `instanceInfo[0]` for a cluster, so a mixed-platform EKS finding unshared one document and left the other shared. Completion now unshares every document acquisition resolved, for every instance, and logs an error rather than failing the acquisition if a removal does not take
- **The acquisition document accepted an object it had not written.** The capture key is the same on every attempt, so if a second attempt's upload failed *after* `tee` had finished - the pipeline still succeeds - `head-object` returned the **first** attempt's object. That was then accepted, reported as the second tool's capture, and published with the first tool's digest and provenance. `verify_capture` now takes the attempt number and requires the stored object's own `acquisition-attempt` to match. Reproduced in a container by failing attempt 2's upload after it consumed all of stdin
- **The recorded AVML version was the pin, not the binary that ran.** An operator-staged binary can be any build, so `acquisition-tool-version` could attribute a capture to a version that never touched the host - a false provenance claim on evidence. The document now asks the binary (`avml --version`) and records that, noting rather than failing if a digest-verified release disagrees with its own pin. The same call makes a staged file that cannot execute - a text file, the wrong architecture - fail immediately and by name, instead of waiting out the listener's 180 second accept timeout for a connection that can never arrive
- **`resolve_artifact_metadata` classified digest files by their last filename fragment and read only the first page of results.** `for part in key.split("_"): is_sha_256 = "sha256" in part` has no `break` and no accumulation, so only the final fragment counted: `vol_sha256_part1.txt` was classified as *not* a digest file and the code then went looking for a digest of the digest. `list_objects_v2` also returns at most 1000 keys per call and was not paginated, so a case prefix holding more than that reported metadata for the first page only - the same shape of bug as the unpaginated `DescribeInstanceInformation` calls already fixed elsewhere in this solution
- **Memory acquisition chose the SSM document once per finding rather than once per instance.** The document was resolved before the loop and only ever reassigned inside it, so in a finding naming both a Windows and a Linux instance the Windows document leaked onto every Linux instance after it - winpmem sent to a host that has no winpmem. The command itself was accepted, so the failure surfaced as an SSM command failure rather than as an unsupported platform, and that instance's memory was never captured
- **A Red Hat `x.0` release matched none of the version branches.** The comparisons were open at the lower bound - `9 > float("8.0") > 8` is false - so RHEL 8.0 fell through all three and `rhel_version` kept whatever the previous instance in the loop had set, or was unbound on the first one. In a finding with a RHEL 9 instance ahead of a RHEL 8.0 one, *both* failed looking for `RHEL9_LIME_MEMORY_ACQUISITION`, which is not deployed. An unsupported Red Hat release now says which release and that no document exists for it, and does not take the supported instances in the same finding down with it
- The forensic tools loader no longer reports success to CloudFormation when the build failed. A zero-byte symbol table is deleted rather than left in the evidence bucket, where its mere presence satisfied downstream checks and produced empty forensic results. An absent artifact is reported as a warning, since both consumers fall back and the symbol table that matters is built per kernel release on demand
- The forensic tools loader terminates its builder instance on every path. Previously each deployment leaked a running instance
- The SSM command waiter used botocore's 100 second default, shorter than any real LiME or dwarf2json build, so the outcome was never observed
- The Amazon Linux 2 tool pre-seed now installs a compiler and kernel headers before compiling LiME, and passes `-y` when installing `kernel-debuginfo`, which SSM's non-interactive shell previously aborted. Artifacts are only uploaded once they exist and parse
- Memory analysis refuses to run against a Volatility 3 older than 2.28.0, which parses a Linux 6.12+ capture without error but walks no tasks, and rejects empty or malformed symbol tables
- Corrected the volatility3 S3 prefix and an unexpanded shell test in the memory load investigation document
- The plaso containers run as `--user 0:0`. Moving the analysis work area off tmpfs onto the EBS volume at `/data` put it on a root-owned `0755` directory, where the non-root user inside `log2timeline/plaso` cannot write; the previous `/tmp` bind happened to be mode `1777`. Both investigation documents failed with `Unable to write to storage file`, which the memory document then reported as a failed investigation even though every Volatility 3 plugin had succeeded and its output had already been uploaded
- The memory investigation no longer attributes an unusable capture to LiME by name, since either tool may have produced it. It points at the `acquisition-tool` metadata instead
- The memory capture is decompressed with `gzip -d -f`, so re-running the investigation on an analysis host that already expanded the image no longer aborts with `already exists`
- **`linux_memcapture_sha256.txt` is now the digest of the memory capture.** The hash was computed by a `tee` whose process substitution inherits the pipe feeding `sha256sum`, and `aws s3 cp` writes its progress lines and its final `upload: - to s3://...` to stdout unconditionally, so those bytes were hashed along with the capture. Every memory capture the solution has ever taken published a digest that does not match its evidence. The uploader is now silenced with `--only-show-errors` and a redirect; verified end to end by recomputing the digest from the stored object
- A plaso failure no longer fails the whole memory investigation. plaso is a filesystem and log timeliner and is supplementary to Volatility 3 on a raw physical memory image, so a complete, valid memory analysis was being reported to the state machine as `MEMORY_INVESTIGATION_FAILED`. A partial `timeline.plaso` or `webhist.csv` is removed rather than uploaded as evidence
- `performMemoryAcquisition` sends `s3bucket`, so the acquisition documents can find the LiME module pre-built for the target's kernel release. Without it the parameter kept its placeholder default and the download was attempted against a bucket literally named `S3 bucket Location`, so every acquisition fell through to compiling LiME on the instance under investigation. It is sent only to the documents that declare it, because SSM rejects `send_command` outright when a parameter is not declared
- **Disk acquisition completes in a single-account deployment.** `shareSnapShot` skips sharing when the application account *is* the forensic account, but it also skipped setting `isSnapshotShared`, which downstream is a phase marker rather than a record of an API call: `checkCopySnapShotStatus` only writes `isSnapShotCopyComplete` on the sharing-complete branch, and the `Is Copy SnapShot Complete` choice reads exactly that path. Every single-account disk acquisition therefore died with `States.Runtime` "invalid path" *after* the snapshot had been taken, copied and its parent triage execution failed with it

Two separate disk investigations failed with `InsufficientInstanceCapacity`, first on m4.2xlarge and then on m6i.2xlarge, both times *after* the snapshots had been taken, so the case was lost for a reason unrelated to it. `forensicInstanceType` now accepts a comma-separated preference order and defaults to `m6i.2xlarge,m6a.2xlarge,m5.2xlarge,m5a.2xlarge` (all 8 vCPU / 32 GiB, so interchangeable here). Capacity errors move to the next candidate; a malformed request still fails immediately

Read access is now `s3:GetObject`/`GetObjectVersion` on the staged tools prefix and on that case's own prefix, which the document reads back to confirm the capture landed. A malformed ARN in the same statement, produced by a missing comma between two f-strings, is also gone

Both read a single unfiltered page - 10 managed nodes by default, 50 at most - so in any account with more managed nodes the target was reported as "SSM not installed" and skipped, or the freshly launched analysis instance was not found and the investigation reported success having produced nothing

Both ended in an unconditional `exit 0`, so the tools loader custom resource reached CREATE_COMPLETE with nothing usable in the bucket. `dwarf2json` also runs unprivileged now rather than as root. Both documents were then run on a live AL2 instance and passed: `kernel-debuginfo` installed, and the profile document produced a valid 34 MB symbol table for kernel 5.10.118 containing 147,261 symbols with the matching LiME module alongside it. The README previously said AL2 memory analysis was unsupported partly because `kernel-debuginfo` was no longer installable; that was wrong and is corrected

- `linux-disk-investigation-prepare` has its shebang on line 1 - it was on line 2, where it is a comment - and checks that the volume actually mounted. An unchecked `mount` reported Success and the disk investigation then ran plaso against an empty directory
- **The evidence volume is mounted at a device that exists.** `attachEBSSnapShot` asked EC2 to attach the volume at `/dev/sdg` and then told the SSM document to mount `/dev/xvdg1`. EC2 only honours the requested name on the Xen instance families; every instance type this solution uses for analysis is Nitro, where the kernel enumerates EBS volumes as `/dev/nvmeXnY` and udev provides the requested `/dev/sdg` but never `/dev/xvdg`. So every disk investigation - Linux and Windows - named a device that could not exist and stopped at the mount. This is the same class of bug as the user-data fix above, on the other side of the same volume. The document now treats the name as a hint and resolves the real partition from the volume id, which NVMe reports as its serial with the dashes removed and which is therefore the one identifier stable across both. Verified on a live m6i.2xlarge: with volumes attached at `/dev/sdf` and `/dev/sdg`, `/dev/sdf1` resolved to `/dev/nvme1n1p1` while every `/dev/xvd*` form was absent, and a deliberately wrong `/dev/sdz1` still resolved correctly from the volume id
- **The mount names the filesystem, and mounts evidence read-only.** The mount specified no type, which fails for two of the three cases this solution actually produces. A Windows evidence volume could not be mounted at all: Amazon Linux 2023 ships no `ntfs-3g` in any of its repositories (`dnf list --available ntfs-3g` returns nothing), and although its kernel carries the in-tree `ntfs3` driver, blkid reports the type as `ntfs` while the kernel registers `ntfs3`, so a bare mount fails with `unknown filesystem type 'ntfs'`. An XFS evidence volume cloned from an instance built on the same AMI as the analysis host - the normal case, since both are Amazon Linux 2023 - carries the same filesystem UUID as the host's own root, and XFS refuses to mount a duplicate. Both were reproduced on a live host before being fixed, the second with a verified UUID collision, and both now mount. Evidence is mounted `ro`, which it was not before: a writable mount of an acquired volume is a chain-of-custody problem regardless of intent
- `windows-disk-investigation` is verified end to end. Run against a mounted Windows Server 2019 volume it produced a 14 MB plaso storage file and a 16,409-row timeline from `EVT` and `FILE` sources, hashed it and published all three artefacts
- **SSM command output is archived to CloudWatch, which it never was.** Every Lambda already set `CloudWatchOutputEnabled: true`, but `AmazonSSMManagedInstanceCore` carries no CloudWatch Logs write permissions, so the agent could not create the log group and the archiving was silently a no-op for every command the solution has ever sent. SSM itself keeps only the first 24 KB of a command's output and volatility3's progress output alone exceeds that, so a failing memory investigation lost precisely the lines that said why - two failures in this account were undiagnosable for that reason. The instance role is now granted `logs:CreateLogGroup`, `CreateLogStream`, `PutLogEvents` and `DescribeLogStreams`, scoped to one prefix rather than every log group in the account, which is only possible because the log group is no longer named after the forensic id alone: `ssm_output_log_group()` puts it under `/aws/ssm/forensic-orchestrator/`. Verified live - six streams across the target and two analysis hosts, carrying the real command transcript. A drift test asserts the CDK and the Lambdas still agree on the prefix, because if they diverge the archiving silently stops again
- **An unassumable application-account role now says what to do about it.** Every Lambda reaches the instance under investigation by assuming `ForensicEc2AllowAccessRole-<region>`, on the first API call of an incident. When that role is absent the error names two roles and explains neither, and in a single-account deployment reads as "cannot assume a role in the account I am already in" - which is genuinely confusing, because the same-account shortcut in `create_aws_client` is gated on `app_account_role` being unset while the CDK always sets `APP_ACCOUNT_ROLE`, so it never fires. The failure now names the role, the account, the template and its two parameters, and in the same-account case explains why a role is needed at all. Deliberately not a fallback to a local client: the Lambda roles are not granted what this role holds - `ssm:DescribeInstanceInformation` on the triage role is an implicit deny, confirmed by policy simulation - so falling back would trade one AccessDenied for a less obvious one deeper into the incident. Throttling and other errors still propagate unchanged, so a transient failure is never reported as a missing prerequisite

That is deliberate and worth keeping - the capture is already downloaded and decompressed under `/data`, and reading a retained host is how the empty-capture failure was identified at all - but nothing said so. Two m6i.2xlarge instances sat running after two failed investigations with no mention in the notification, no entry in the forensic record and no owner. The failure notification now names the instance, says the retention is deliberate, says where the evidence is and that closing the case means terminating it, and the same goes into the forensic timeline. A test asserts `terminateForensicInstance` has not been added to the failure chain, because doing so would destroy the only surface a failure can be diagnosed from
- **The empty-capture diagnostic reported the opposite of the truth.** `tr -d '\000'` was written in the document JSON as `'\\\\000'`, which decodes to `'\\000'`, so the shell deleted backslashes and the character `0` rather than NUL bytes. A capture that was 97.7% NUL was reported as "2086487539 of 2086711456 bytes non-zero" - in the single message whose whole purpose is telling the operator to re-acquire. The banner check that gates the failure was correct, so the failure still fired; only the number an operator would act on was wrong. `test/ssm-document-invariants.test.ts` now rejects a doubled backslash reaching the shell in any document
- **dwarf2json now comes from the project that owns it, pinned and digest verified.** `amazon-linux-2-volatility-profile` fetched it from an individual's repository (`kevthehermit/volatility_symbols`) off the default branch, with no tag, no signature and no digest, and then ran it against the kernel's debug symbols. Whoever controlled that branch controlled a binary reading `vmlinux` on the builder. It is now the `volatilityfoundation/dwarf2json` release binary at `v0.9.0`, verified against `e2e75ba5bc9c22bc38a48edffbb050456d089d54998d54f46cb580223d9fbc6b` before it is made executable, and a mismatch aborts rather than warns. The digest was cross-checked against the asset size GitHub reports (2,986,584 bytes). Using the release binary rather than building from source, as the AL2023 and RHEL8 siblings do, avoids requiring a Go toolchain on an end-of-life Amazon Linux 2 builder. Verified end to end on a live AL2 instance: the document produced a valid 25 MB symbol table for kernel 4.14.355 with 102,393 symbols, and the ISF records `producer: dwarf2json 0.9.0`, which only appears if the pinned binary is the one that ran
- **A target that stops answering mid-acquisition is now contained before the execution fails.** `checkMemoryAcquisitionCompletion` already caught its errors, so the failure was reported cleanly, but isolation sits further down the happy path and was skipped. That is the wrong way round for the case that actually happens: the status check fails because the instance stopped answering SSM, which is exactly when containment matters, and isolation does not need SSM - it swaps the security group, revokes sessions and sets termination protection through the EC2 and IAM APIs, all of which still work against a host that has gone dark. The catcher now routes through a choice that isolates only when isolation was requested, then fails regardless, and a failed isolation does not mask the acquisition failure. Strictly additive: when the flag is absent or false, which is every triage that did not ask for containment, the behaviour is exactly as before

### Upgrade notes

Three changes in this release cannot be undone by editing configuration afterwards. Read them before upgrading from 1.3.2.

- **`forensicImageName` is renamed from `sansift` to `forensic-analysis-ami`, which replaces the SSM parameter.** That context value *is* the physical name of the parameter `createForensicInstance` reads, so the upgrade creates `forensic-analysis-ami` and deletes `sansift`. The new parameter starts at the `ec2ForensicImage` context value, or at `n/a` when that is empty, so **any AMI id written into `sansift` outside CloudFormation is discarded** and no investigation can launch an analysis instance until the image pipeline publishes an AMI or `ec2ForensicImage` is set. To keep the existing parameter and its value, set `forensicImageName` back to `sansift` in `cdk.json` before deploying
- **`ForensicImageBuilderStack` pins the VPC and subnet of `ForensicSolutionStack`.** The build instances run in the forensic VPC, so the solution stack now publishes two CloudFormation exports (`ForensicSolutionStack:ExportsOutputRefforensicInfravpc...` and `...forensicInfravpcserviceSubnet1Subnet...`). While the image builder stack exists, `ForensicSolutionStack` can never rename, replace or remove the forensic VPC or its first `service` subnet, because CloudFormation refuses to delete an export another stack imports, and tearing the solution down has to be `cdk destroy --all` rather than `cdk destroy ForensicSolutionStack`. Setting `imageBuilderPipelines` to `[]` removes the stack and both exports with it
- **Pinning `ec2ForensicImage` does not stop the image pipeline.** The pin is honoured, in that the pipeline no longer overwrites the AMI SSM parameter, but the pipeline is still created, still builds an image during the deployment (`buildOnDeploy`) and still rebuilds on `buildSchedule`, monthly by default. None of those AMIs is ever consumed while the pin is in place, and each build costs a `t3.large` instance plus AMI and snapshot storage. Set `buildOnDeploy: false` and `buildSchedule: ""` on the entry in `imageBuilderPipelines`, or remove the entry altogether, if the pinned AMI is the one you intend to keep using
